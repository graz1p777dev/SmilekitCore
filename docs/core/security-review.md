## Найдено в существующем коде (не исправлено)

Это места вне сегодняшней задачи. Каждое — правка на несколько строк, но
требует вашего решения по ролям, поэтому сам не трогал.

### 1. Выключатель бота доступен любому сотруднику — важно

`src/actions/amocrm-bot.ts` — `setAmoBotEnabled()` и `getAmoBotEnabled()`
работают через админ-клиент (в обход RLS) и **не проверяют роль вообще**.
Middleware требует лишь активную сессию, значит любой вошедший сотрудник —
включая роль `pending` — может выключить бота продаж на проде. Обнаружить это
по логам нечем: действие ничего не пишет в аудит.

Как чинить: та же проверка `requireOwner()`, что и на новой странице
«Интеграции» (там переключатель уже закрыт владельцем). Нужно решение: только
владелец или ещё РОП.

### 2. Секреты вебхуков сравниваются обычным `===` — низкая

`api/amocrm/webhook` (`?secret=`), `api/whatsapp/webhook` (`?secret=`),
`api/internal/deals`, `api/internal/orders`, `api/internal/notify`
(`x-internal-token`). Через сеть подбор по таймингу малореален (джиттер
перекрывает разницу), но лечится одной строкой — `timingSafeEqual`, как уже
сделано в канале Green API.

Отдельно: секрет в query string амо- и wazzup-вебхуков попадает в логи любого
прокси на пути. Перенести в заголовок можно только вместе с настройкой на
стороне провайдера.

### 3. У маршрутов вебхуков нет ограничения частоты — низкая

`api/greenapi/webhook` и соседние: с валидным токеном можно залить очередь
обработки. Токен знает только провайдер, поэтому риск скорее «сбойный
провайдер», чем атака. Потолок параллельной обработки в ядре (4 чата) уже
ограничивает ущерб.

### 4. Переписка клиентов видна всем сотрудникам — по решению бизнеса

`amocrm_messages`, `bot_messages`: политика `SELECT ... USING (TRUE)` для
`authenticated`. Для отдела продаж это, скорее всего, и нужно; отмечаю, чтобы
это было осознанным решением, а не случайностью.

## Остаточные риски нового контура

Их нельзя закрыть кодом полностью — важно про них знать.

1. **Ключ шифрования — единственная точка отказа.** `INTEGRATION_ENCRYPTION_KEY`
   лежит в Railway. Потеряли или сменили — сохранённые токены не расшифруются
   (в логах будет видно, какие), их вводят заново. Доступ к переменным Railway
   = доступ ко всем токенам CRM.

2. **Владелец = максимальные права.** Кто вошёл владельцем, тот правит адреса
   вебхуков и тексты, которые бот шлёт клиентам. Отсюда практический вывод:
   у владельца должен быть включён второй фактор в Supabase Auth, а
   «общий» аккаунт владельца на несколько человек — плохая идея.

3. **SSRF закрыт по адресу, но не по DNS.** Домен, который резолвится в
   `10.0.0.5`, проверку пройдёт: она смотрит на имя хоста, а не на итоговый IP.
   Полное закрытие — резолвить адрес перед запросом и запрещать приватные сети,
   с защитой от rebinding. Стоит делать, если вебхуки будут править не только
   владелец.

4. **Регулярки в условиях пишет человек.** Ограничения по длине снижают риск,
   но не убирают: у Node нет таймаута на regex. Если появятся жалобы на
   «подвисания» — смотреть в первую очередь на ветки с `matches`.

5. **Данные клиента уходят по адресу из настроек.** Действие «дёрнуть вебхук»
   отправляет номер и текст сообщения на указанный адрес. Это осознанный выбор
   владельца, но помнить о нём стоит: персональные данные покидают контур CRM.

## Что проверено и вопросов не вызвало

- `.env.local` в репозиторий не закоммичен (`git ls-files`).
- В браузер уходят только `NEXT_PUBLIC_SUPABASE_URL` и `..._ANON_KEY` —
  сервисный ключ в клиентский код не попадает.
- Прокси к бэкенду бота (`api/backend/[...path]`) закрыт allow-list'ом по роли
  и методу: новый эндпоинт по умолчанию доступен только владельцу.
- Единственный `dangerouslySetInnerHTML` (`GlowOrb.tsx`) вставляет статический
  CSS без пользовательских данных.
- Серверные действия страниц «Интеграции» и «Сценарии» проверяют роль владельца
  в каждой функции, включая чтение.
- Отправка сценариев идёт через `chat.send`, то есть сценарий с канвы не может
  обойти предохранители ядра (менеджер в чате, отписка, выключенный бот).
